shell script to query the version of a particular package in nixpkgs master/nixos-unstable:

#!/usr/bin/env bash

cd ~/src/nixpkgs || exit 1
git fetch origin --quiet

master_rev="$(git rev-parse origin/master)"
nixos_unstable_rev="$(git rev-parse origin/nixos-unstable)"

unstable_version="$(nix eval --raw "./?rev=$nixos_unstable_rev#$1.version")"
echo "unstable: $unstable_version"

master_version="$(nix eval --raw "./?rev=$master_rev#$1.version")"
echo "master:   $master_version"

I have had a lot of discussions over the last decade on correct handling for out-of-memory conditions. There are two very distinct philosophical camps.

The Windows kernel has a policy of 'don't make promises you can't keep'. This means that a call to malloc will either return memory that is already available or the result of a new call to VirtualAlloc2, with committed memory. When the NT kernel says it has 'committed' memory, it means it promises that memory will be available when you try to access it. There is space reserved either in RAM or in swap to permit something else to be moved from RAM to make space for the thing that you need.

The other extreme says that you should assume that sometimes components fail. Erlang embodies this as the 'let it crash' philosophy. Google discovered fairly early on that, when you're looking at jobs distributed across large fleets of machines, a single node experiencing hardware failure is basically unavoidable. Mainframes deal with this by duplicating all of the hardware (often multiple times) so a hardware failure can be transparently worked around. But clouds built from consumer hardware don't do that: sometimes VMs die and you deal with it.

In the 'let it crash' model, you already need to build resilience at a higher level. Your individual jobs may fail because the hardware that runs on them fails. You need to be able to roll back any partially committed transactions that they started and restart them from the beginning. For things like web servers, that's usually easy: This HTTP request failed? The client can retry.

Once you have that mechanism, you rapidly realise that you can use it for other infrequent operations. Memory allocation almost never fails. If it does, let the program crash. Systems like iOS and macOS encourage programs to persist any user-visible state frequently, so a program crashing is fine - you may lose a couple of seconds work. In exchange for this, you get much simpler code. Rather than every allocation having to come with error handling (and there are tens of thousands of individual allocation points in a typical non-trivial program), you just assume it works and crash if it failed.

Some kernels, such as Linux and FreeBSD, lean into this even further. If the kernel claims it's given you memory, that isn't a promise, it's a best-effort guarantee. When you actually use it, they'll either ensure it's there or deliver a signal. It turns out most programs ask for memory that they'll need in their worst case, but this mechanism gives them the memory that they actually need. And this means that fewer allocations fail. You can't easily handle the allocation failure locally, but you're now less likely to hit allocation failure.

And this is a big win for overall reliability and performance. Because it turns out that gracefully handling out-of-memory conditions is really hard. Often, good error recovery requires allocating memory, but you can't do that if you've hit an out-of-memory condition. And these errors propagate outwards. Every function that allocates memory not may fail due to memory exhaustion. So it's not just routines that allocate memory that need to handle out-of-memory errors, it's everything that calls them. And you have to get it right at every place that needs to do any kind of cleanup if memory is exhausted.

This is one of the biggest reasons that embedded development is harder than application development: you can't assume memory exhaustion is rare and you don't always have an outer layer that can handle component-level failures. But in every other situation, the correct approach is to assume that memory is infinite and allocations never fail, and to assume that the component making that assumption will crash periodically.

The Phermi Paradox

If #PHP2Shell is so gnarly and so many systems are vulnerable, why hasn't half the internet fallen over?

Couple possibilities:

1. The exploit is still non-trivial and building the full attack chain is taking some time.

This is at least partially true. I've yet to see a fully reliable proof-of-concept exploit that addresses all versions of PHP. Calif and Wiz showed exploit videos against targets. They didn't show what pregaming they did to prepare the exploit for those specific targets. So far, it seems like some prior work is necessary to get proper offsets, heap layouts, and payload shapes to exploit properly.

And that's assuming the mod_php SAPI, which responds differently to this than PHP-FPM.

2. Patching was aggressive and major targets had time to get in front of this.

For larger orgs, I believe this is accurate. The message was clear enough, and there was time enough to get any org with a half-awake IT team to circle the wagons. Patching isn't done, surely, but I think the most enticing targets for notable attacks probably moved quickly.

It's also worth noting that status dashboards like this are mostly a fairy tale. Look at the bottom for some whopper disclaimers. OS backports to versions other than PHP's official patched versions will muddy the picture, as will the 50% of PHP services that don't report versions. I'm not saying most of the internet is patched; I'm just saying

But let's not ignore the alternative:

3: The exploited won't know it's happening and won't report it.

This is hardly a new phenomenon PHP sites have been exploited for years without anyone noticing (see: Slot Gacor). Exploitation won't look like the internet blinking off. It'll look like a bunch of gambling pages and piracy hosted on school and municipal government websites. Such attacks can lie quietly on PHP sites for years before anyone bothers to look.
