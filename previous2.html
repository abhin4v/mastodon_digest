One thing about mathematical conjectures is that there's no guarantee that they're feasibly solvable. I suspect that if you choose conjectures at random, their difficulty is a very heavy tailed distribution. The Millennium Prize Problems might actually be easier than average in this sense. They're each part of a large body of theory, which I suspect makes them tamer than simpler problems with less structure.

Even if the galaxy is turned into a giant computer, I suspect at least one of the following conjectures will stand for a million years.

1. The Collatz Conjecture
2. π^(π^(π^(π^π))) is an integer
3. The fractional part of e^n tends to 0
4. All Fermat numbers are square-free
5. The Ramsey number R(6, 6) is prime
6. TREE(5) is prime
7. The decimal expansion of √3 contains only finitely many 6s
8. There exists an odd perfect number
9. The largest power of 2 with all even digits is 2048
10. 41 disjoint 4-spheres can all touch a central 4-sphere of the same size

Even if one of them is solved tomorrow, it wouldn't matter. The minimum of some samples from a heavy tailed distribution says very little about the maximum.

@mcc My -rough-understanding of compile-time logic is that it runs in a slightly different set of semantics than runtime logic, exposing various bits of type info in the process.

std.debug.print is written using the comptime logic, for example, and it does comptime parsing of the format string, while also reflecting over the anonynous struct that is the second parameter.

Which means that std.debug.print's format string argument must be a comptime constant, not a dynamically provided u8 array. It also means that std.debug.print's level of compile time type check is available to your code.

The comparision points I have seen made are to OCaml modules, or a sort of duck typing.

This is paired with the fact that Zig's compiler doesn't run type checking or any analysis beyond basic syntax parsing on code that isn't reachable from an execution root. So you can write 

fn add(T: type, a: T, b: T) T { return a + b; }

And it will compiler error if you call it with types that zig doesn't know how to +

I personally think that the widespread use of AI has multiple reasons. Each of these forms a strong, local pattern.

One of them would be people who programmed at the edge of their ability, relying a lot on StackOverflow and the like for details (that used to be pretty common, I think) or didn't have enough familiarity with regular expressions and command line tools or automations within their editor to do large text transformations. Fine, we should have written better tools, our tools should have had better integration, StackOverflow should have been non-gamified and less of a place where people grow cold and bitter over the years. I used to be a big fan! Also web-sites replaced good local documentation like man pages, info pages, local help sites. I see the effect these days where I try to use Zeal to find information in local copies of MDN and programming language documentation, for example. What a game changer! Also some programming languages like Java require a lot of formalism (boiler plate code), which is doable if you are intimately familiar with your editor and know how to make it useful (but many did not); if you lived in your own private code where you could write abstractions and use them, then perhaps LLM-generated code is far less useful.

Another strong, local pattern that I've seen is people being overwhelmed by the modern world, basically. In my family, I see them overwhelmed with contracts in all its forms, a new work contract, choosing a new phone service provider; they are overwhelmed with the breadth of problems they are facing like how to fix a leaking roof; how to make a claim with the insurance. The world is complicated and there are always people trying to create new services and new options and new products therefore -- automatically! -- the world is as complex as it can possibly be. Any more and whatever you want to add won't sell. Any simpler and somebody will identify this as a niche and have something to sell. And with all of us and all our abilities (the sum of many independent measures) forming a bell curve, there are always some of us struggling. This appears to be inevitable unless we make an extra effort. And since we don't, here we are. I know that we try to make efforts to simplify and help the elderly, the children, and so on. But it's not enough and it leaves all the "adults" in the room to struggle all the same. The LLMs appear somewhat useful to such people.

Another strong, local pattern that I've seen is the importance of literacy and its lack. All around us we see that expressing ourselves well is important to our careers, to making ourselves heard. And yet not everybody can do it. And even if we attempt to teach it, not everybody wants to spend the effort. There is a finite amount of fucks to give, of spoons to have, of energy for all the things in life. And for some people, reading and writing is not it. So if literacy is important and you struggle with it, LLMs appear to be useful.

I'm sure that if we'd spend more time on this, ask around, we'd eventually be able to find some abstract pattern here: something is valued but it's difficult and the LLM makes it easier. The solution to having LLMs infest everything would therefore seem to be to make the other things less essential, easier. And we also see how future exploitation will happen: things will remain difficult and LLM help will cost money. It's great for those who know how to do the difficult thing and for those who make the LLMs.

I guess I'm grappling with a way forward for me individually and as a society, being an LLM hater. I could, for example, offer to help do the thing that the LLM is doing for friends and family. Even just being around friends and family so that there will be more occasions where we can interact so that people can ask without it being a thing. To insist on processes to be simple, to argue for solutions that don't dump all the complexities of systems on end users, on buyers, on clients.
